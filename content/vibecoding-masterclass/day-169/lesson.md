## 【第 169 天：MLOps A/B 測試與漸進式部署策略】 - 讓你的模型聰明又安全地升級！

### 前言：模型部署，不是「丟上去」就好！

想像一下，你辛辛苦苦訓練出一個新的、更棒的機器學習模型 (v2)，它在測試資料上表現超級好！你迫不及待地想讓它上線，取代舊模型 (v1)。

但等等！直接把 v1 拔掉，換上 v2，真的好嗎？
*   萬一 v2 在真實世界中的表現不如預期呢？
*   萬一它有一些邊緣案例會出錯，導致用戶體驗大打折扣呢？
*   萬一它對系統造成了意想不到的負擔呢？

這些都是真實世界的挑戰！MLOps 不僅僅是訓練模型，更重要的是如何「安全、有效地」將模型部署到生產環境。而 A/B 測試和漸進式部署就是解決這些問題的黃金搭檔！

---

### 一、A/B 測試：讓數據說話，找出最好的模型！

#### 什麼是 A/B 測試？

想像你開了一間線上咖啡店，你想知道是「買一送一」還是「第二杯半價」的促銷活動更能吸引顧客。你會怎麼做？
你可能會把顧客隨機分成兩組：
*   **A 組 (Control Group)**：看到「買一送一」的廣告。
*   **B 組 (Experiment Group)**：看到「第二杯半價」的廣告。

一段時間後，比較兩組的銷售數據，就能知道哪個促銷活動效果更好了！

在 MLOps 中，A/B 測試也是一樣的道理。當你有一個新模型 (v2) 和一個舊模型 (v1) 時，你可以：
1.  將你的使用者或請求隨機分成兩組。
2.  **Control Group**：繼續使用舊模型 (v1) 的預測結果。
3.  **Experiment Group**：使用新模型 (v2) 的預測結果。
4.  監控兩組的關鍵指標 (例如：點擊率、轉換率、錯誤率、延遲等)，然後用數據證明 v2 是否真的優於 v1。

#### 為什麼要 A/B 測試？

*   **避免盲目部署：** 實驗室的表現不等於真實世界的表現。A/B 測試能讓你用真實數據來驗證模型。
*   **量化影響：** 清楚地知道新模型帶來了多少提升 (或下降)，為決策提供依據。
*   **降低風險：** 在小範圍內測試新模型，避免對所有用戶造成不良影響。

#### 程式碼範例：如何將用戶分組？

在實際系統中，你會根據用戶 ID 的 Hash 值或其他方式來分配，確保同一用戶總是分到同一組。這裡我們用簡單的隨機數來模擬。

```python
import random

def assign_user_to_ab_group(user_id):
    """
    根據用戶 ID 將用戶分配到 A 或 B 組。
    在實際應用中，通常會基於用戶 ID 的 hash 值來確保每次分配一致，
    這裡為了簡化，直接使用隨機數。
    """
    if random.random() < 0.5: # 50% 機率分到 Control 組
        return "control"  # 使用舊模型 (v1)
    else:
        return "experiment" # 使用新模型 (v2)

# --- 模擬情境 ---
print("--- 模擬 A/B 測試用戶分組 ---")
user_ids_to_test = ["user_alice", "user_bob", "user_charlie", "user_diana", "user_eve"]

for user_id in user_ids_to_test:
    group = assign_user_to_ab_group(user_id)
    print(f"用戶 {user_id} 被分配到 {group} 組。")

    # 實際應用中，你會根據 group 決定要呼叫哪個模型服務
    if group == "control":
        print(f"  -> 為用戶 {user_id} 提供舊模型 (v1) 的預測。")
        # 调用 model_v1.predict(data)
    else:
        print(f"  -> 為用戶 {user_id} 提供新模型 (v2) 的預測。")
        # 调用 model_v2.predict(data)
    print("-" * 20)
```
執行這段程式碼，你會看到用戶被隨機分到不同的組，然後我們就可以根據分組來選擇使用哪個模型。

### 二、漸進式部署：小心翼翼，確保模型平穩過渡！

#### 什麼是漸進式部署 (Gradual Rollout / Canary Deployment)？

假設你的新模型 (v2) 已經通過了 A/B 測試，證明它確實更優秀了！太棒了！現在你可以放心地把它部署上線了，對嗎？

但即使 A/B 測試通過，大規模部署時還是可能出現意想不到的問題，例如：
*   模型在流量高峰時資源使用過高，導致服務變慢甚至崩潰。
*   與其他系統的整合在極端情況下出錯。
*   記憶體洩漏等長時間運行才會顯現的問題。

這時候，**漸進式部署**就派上用場了！它就像是「溫水煮青蛙」的反向操作，我們不是一次性替換所有流量，而是**逐步將一小部分流量導入新模型**，然後慢慢增加這個比例，直到所有流量都切換到新模型為止。

最常見的漸進式部署策略是 **金絲雀部署 (Canary Deployment)**。就像煤礦坑裡的金絲雀，我們把新模型當作金絲雀，先讓一小部分流量去「試水溫」。如果金絲雀沒事，表示環境安全，我們就慢慢增加金絲雀的數量。

#### 為什麼要漸進式部署？

*   **降低部署風險：** 避免一次性全部切換造成的災難性後果。
*   **即時監控：** 在小流量階段就能發現潛在問題，及時回滾 (Rollback)。
*   **平滑過渡：** 用戶體驗受到的影響最小。

#### 程式碼範例：如何漸進式切換流量？

這裡我們模擬一個服務，它會根據一個百分比來決定是使用舊模型還是新模型。

```python
import random
import time

def get_model_prediction(data, model_version):
    """
    模擬模型預測函數。在實際應用中，會呼叫不同的模型API或服務。
    """
    time.sleep(0.01) # 模擬一點點延遲
    return f"預測結果來自 Model {model_version} for data: {data}"

def gradual_rollout_inference(data, rollout_percentage):
    """
    根據漸進部署比例決定使用新舊模型。
    rollout_percentage: 新模型接收的流量百分比 (0-100)。
    """
    # 如果一個隨機數小於滾動比例，則使用新模型
    if random.random() * 100 < rollout_percentage:
        # print(f"  -> 使用新模型 (v2)")
        return get_model_prediction(data, "v2")
    else:
        # print(f"  -> 使用舊模型 (v1)")
        return get_model_prediction(data, "v1")

# --- 模擬漸進式部署過程 ---
print("--- 模擬漸進式部署 ---")
current_rollout_percentage = 10 # 從 10% 流量導向新模型開始

for step in range(4): # 模擬 4 個部署階段
    print(f"\n===== 階段 {step + 1}: 新模型流量比例為 {current_rollout_percentage}% =====")
    
    # 模擬處理 10 個請求
    for i in range(10): 
        request_data = f"用戶請求_{i+1}"
        prediction = gradual_rollout_inference(request_data, current_rollout_percentage)
        print(f"處理 {request_data}: {prediction.split(' ')[2]} 模型") # 簡化輸出，只顯示模型版本
        
    # 增加部署比例 (通常會根據監控結果手動或自動調整)
    if current_rollout_percentage < 100:
        current_rollout_percentage = min(100, current_rollout_percentage + 25) # 每次增加 25%
    
    # 實際部署中，這裡會有嚴格的監控和檢查點
    time.sleep(1) # 模擬等待一段時間，進行監控

print("\n--- 部署完成！所有流量已導向新模型 (v2) ---")
```
執行這段程式碼，你會看到一開始大部分請求都由 v1 模型處理，隨著 `current_rollout_percentage` 的增加，越來越多的請求被導向 v2 模型，直到所有請求都使用 v2。這個過程中，你會有足夠的時間去監控 v2 的表現。

### 三、A/B 測試與漸進式部署的連結

你可能已經發現了，這兩種策略經常是**相輔相成**的：

*   **A/B 測試**：幫助你**判斷**新模型是否真的更好，值得推廣。它回答「這個模型好不好？」
*   **漸進式部署**：幫助你**安全地推廣**已經被驗證過更好的新模型。它回答「這個模型怎麼部署才安全？」

有時，A/B 測試甚至會發生在漸進式部署的初期階段。例如，你將 10% 的流量分給新模型進行 A/B 測試，如果效果好，就開始漸進式部署，逐步將所有流量切過去。

---

### 重點回顧：

*   **A/B 測試 (A/B Testing)**：透過將用戶隨機分組，同時運行多個模型版本，並比較其指標來確定哪個版本表現最佳。
    *   **目標：** 數據驅動決策，驗證新模型價值。
    *   **關鍵：** 隨機分配、客觀指標監控。

*   **漸進式部署 (Gradual Rollout / Canary Deployment)**：逐步將流量從舊模型切換到新模型，並在此過程中持續監控。
    *   **目標：** 降低部署風險，確保平穩過渡。
    *   **關鍵：** 小比例開始、嚴密監控、隨時準備回滾。
