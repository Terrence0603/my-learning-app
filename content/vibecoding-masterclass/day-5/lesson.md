## 【第 5 天：Part 2: 敏捷開發、MVP 與重構術語】

### 🚀 1. 敏捷開發 (Agile Development)：小步快跑，擁抱變化！

想像一下，你要蓋一棟豪華別墅。傳統的蓋法可能是一開始就畫好所有藍圖，然後一次性地、從頭到尾蓋完，期間不太會改變。如果蓋到一半，屋主突然說他想要一個游泳池，或者發現某個房間的設計不實用，那可能就麻煩了，修改起來成本很高。

**敏捷開發 (Agile)** 更像是你先蓋好一個可以住的小屋（最基本的功能），然後請屋主（使用者）來看看、給建議，甚至住幾天體驗一下。根據這些建議，你再逐步擴建，增加房間、裝修，甚至最後變成豪華別墅。

**敏捷的核心就是：**

*   **小步快跑 (Iterative)**：把大目標分解成許多小任務，每次只完成一小部分，然後快速發佈。
*   **擁抱變化 (Flexible)**：需求是會變的！敏捷鼓勵我們隨時調整方向，而不是死守著最初的計畫。
*   **持續回饋 (Feedback-driven)**：經常與使用者溝通，從他們那裡得到回饋，讓產品越來越貼近實際需求。

這讓我們寫程式時，不用等到所有功能都完美了才發佈，而是可以先推出一個基本版本，讓使用者試用，然後根據他們的需求和回饋，不斷改進和增加功能。這樣不僅風險小，而且使用者也會更滿意！

### 🎯 2. MVP (最小可行產品 - Minimum Viable Product)：先讓它動起來！

承接敏捷開發的概念，**MVP (Minimum Viable Product)**，中文是『最小可行產品』。白話來說，就是你的產品最最核心、最最基本的功能是什麼？先把它做出來！

一個經典的比喻是：如果你想做一輛「車」，MVP 不是先造一個輪胎，再造底盤。因為這些單獨的零件無法滿足「移動」這個核心需求。

*   你的第一個MVP可能是個 **滑板** (能讓你移動)。
*   第二個迭代可能是 **自行車** (能讓你更快地移動)。
*   第三個迭代是 **摩托車** (更省力，速度更快)。
*   最終，你可能才擁有一輛 **汽車**。

這樣做的好處是，你可以很快地把產品推向市場，得到真實使用者的回饋，避免浪費時間開發那些沒人要的功能。重點是「可行 (Viable)」，它必須是一個能運作、能解決問題的完整（儘管簡陋）產品，而不是半成品。

### ✨ 3. 重構 (Refactoring)：打掃你的程式碼房間！

好，當你小步快跑、快速迭代，快速做出 MVP 的時候，程式碼可能會變得有點混亂，就像你的房間一樣，一開始很整齊，但東西越堆越多，久了就亂了。

這時候，『重構』就派上用場了！**重構的意思是：在不改變程式碼『外部行為』的前提下，改善其『內部結構』。**

想想看，你的房間看起來還是個房間，但你重新整理了櫃子，把衣服分類，讓它變得更整潔、更容易找到東西。重構程式碼也是一樣！

**為什麼要重構？**
*   **更清晰、易讀**：別人（或未來的你）更容易理解程式碼在做什麼。
*   **更容易維護**：修復 Bug 或增加新功能時更輕鬆。
*   **減少 Bug**：雖然重構本身不改變功能，但更清晰的程式碼會降低引入新 Bug 的風險。

現在，我們來看一個簡單的程式碼範例，你會看到重構前後的差異：

#### 程式碼範例：訂單金額計算的重構

假設我們有一個計算訂單最終金額的函數，它需要考慮會員折扣和滿額折扣。

**重構前 (Before Refactoring)：**
```python
def calculate_order_price_bad(item_price, quantity, is_member):
    # 原始寫法，可能有些地方不夠清晰
    total = item_price * quantity # 計算小計
    if is_member:
        total = total * 0.9 # 會員打九折
    if total > 100:
        total = total - 5 # 滿100減5元
    return total

print("--- 重構前 ---")
print(f"範例1 (會員, 滿額): {calculate_order_price_bad(15, 8, True)}")   # 15*8=120 -> 120*0.9=108 -> 108-5=103
print(f"範例2 (非會員, 未滿額): {calculate_order_price_bad(10, 5, False)}") # 10*5=50 -> 50 (無折扣)
print(f"範例3 (非會員, 滿額): {calculate_order_price_bad(25, 5, False)}") # 25*5=125 -> 125-5=120
print("-" * 20)
```
**問題分析：**
*   `0.9`、`100`、`5` 這些數字稱為『魔術數字 (Magic Numbers)』，它們的意義在程式碼中不明顯。
*   變數 `total` 被重複使用，可能有點混淆。
*   折扣邏輯雖然簡單，但如果未來有更多折扣，會很難擴展。

**重構後 (After Refactoring)：**
```python
# 定義常數，讓數字的意義更明確
MEMBER_DISCOUNT_RATE = 0.10 # 會員折扣率
MIN_ORDER_FOR_BULK_DISCOUNT = 100 # 滿額折扣門檻
BULK_DISCOUNT_AMOUNT = 5 # 滿額折扣金額

def calculate_final_order_price_good(unit_price, amount, is_premium_customer):
    # 1. 計算商品小計
    subtotal = unit_price * amount

    # 2. 應用會員折扣 (如果適用)
    if is_premium_customer:
        # 使用常數讓計算更清晰：原價 * (1 - 折扣率)
        subtotal *= (1 - MEMBER_DISCOUNT_RATE)

    # 3. 應用滿額折扣 (如果適用)
    if subtotal > MIN_ORDER_FOR_BULK_DISCOUNT:
        subtotal -= BULK_DISCOUNT_AMOUNT

    return subtotal

print("--- 重構後 ---")
print(f"範例1 (會員, 滿額): {calculate_final_order_price_good(15, 8, True)}")   # 103
print(f"範例2 (非會員, 未滿額): {calculate_final_order_price_good(10, 5, False)}") # 50
print(f"範例3 (非會員, 滿額): {calculate_final_order_price_good(25, 5, False)}") # 120
print("-" * 20)
```

**重構後的改善：**
1.  **可讀性 (Readability)**：我們引入了 `MEMBER_DISCOUNT_RATE`、`MIN_ORDER_FOR_BULK_DISCOUNT` 等常數，讓這些數字的意義一目了然。
2.  **可維護性 (Maintainability)**：如果折扣率或門檻需要修改，只需要更改常數的值，而不是到處找 `0.9` 或 `100`。
3.  **清晰的邏輯 (Clear Logic)**：每個步驟的計算都更加明確，易於理解。
4.  **外部行為不變**：最重要的是，兩個函數執行相同的輸入，會得到相同的輸出結果！
